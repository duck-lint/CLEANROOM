# Clean-Room Protocol

## Purpose

This protocol preserves the existing CLEANROOM work while preventing both accidental Python architecture and clean-room prose from being treated as a substitute for corpus contact. Clean-room discipline means authority hygiene, not corpus avoidance.

## 1. Domain-scoped authority

```text
Constitutive system meaning
    Organon
    explicit operator decisions

Runtime semantic authority
    accepted kernel equations
    accepted runtime invariants

Corpus actuality
    raw authored-vault structure and content
    including irregularities, absences, ambiguity,
    malformed structures, and unresolved authoring states

Representational authority
    corpus-validated semantic contracts

Implementation authority
    accepted implementation contracts
    within their explicitly declared responsibility
```

The Organon constrains system meaning. Explicit operator decisions resolve open authoring or constitutive questions. The vault supplies authored instances and irregularities. Equations and invariants constrain deterministic authority. Contracts become representational authority only after corpus validation. Implementations are authoritative only within their accepted boundary.

No domain silently overrides another. A conflict requires:

```text
classification
→ retained evidence
→ explicit operator or contract decision
→ bounded amendment
```

## 2. Evidence taxonomy

These evidence classes must remain distinguishable:

```text
raw authored-vault observations
Python materialization observations
runtime traces and measured behavior
private-UAT reports
synthetic fixtures
implementation source and diagnostics
operator attestations
```

Evidence may establish a required capability, concrete consumer, corpus phenomenon, failure mode, contradiction, unsupported assumption, performance or scale condition, or need for an explicit amendment. It does not silently acquire semantic authority. Observed Python success does not prove Python architecture; private UAT may establish behavior without validating internals; synthetic fixtures establish local deterministic mechanics, not corpus actuality; implementation source establishes what code does, not what the system ought to mean.

## 3. Operator-attested recovery baseline

The operator attests that complete-vault ingest occurred; real corpus questions were answered; exact, lexical, vector, graph, and temporal mechanisms operated; multi-turn private UAT exercised the system; and useful whole-corpus behavior resulted. This is an `operator-attested recovery baseline`, not an unqualified architectural fact.

It does not establish Python ontology correctness, exhaustive projected affordances, preservation of CLEANROOM equations or invariants, evidence-admission correctness, absence of accidental semantic/coherence gates, correctness of candidate Rust contracts, correctness of Python boundaries, or corpus-scale suitability of candidate Rust activation.

The required recovery-baseline manifest records where available:

```text
python_repository_commit
corpus_snapshot_identity
inventory_identity
materialization_or_index_identity
private_uat_suite_identities
report_identities
demonstrated_capabilities
known_failures
known_architectural_violations
unmeasured_areas
private_artifact_hashes_or_locations
attestation_timestamp
```

`materialization_or_index_identity` is historical observed recovery evidence
where available, not a requirement that future CLEANROOM runtime access carry
an independent materialization identity. Unknown historical values remain
`unknown`; no future identity is inferred or fabricated before Phase 7 builds
concrete access machinery.

Unknown or unavailable identities are represented as `unknown`; no historical identity is inferred or fabricated.

## 4. Clean context and pre-admission observation

The kernel repository remains independent. Corpus contact uses explicit artifacts rather than ambient legacy context: the Organon, raw authored-vault observations, versioned substrate bundles, projection validation reports, redacted behavior/UAT reports, accepted schemas, and synthetic regression fixtures.

Observation precedes classification or admission. The authored observation layer exposes, as available:

```text
source path
source identity and UUID observation
raw frontmatter keys
raw frontmatter value shapes
frontmatter source provenance
heading hierarchy
authored Markdown block candidates
raw Markdown
wikilinks
aliases
embeds
heading targets
block targets
source spans
parse failures
unsupported syntax
ambiguous targets
unresolved targets
source hashes
corpus snapshot identity
```

These are not yet semantic objects, semantic units, identifiers, or occurrences. Relevant facts are classified as `admitted`, `quarantined`, `rejected`, `unresolved`, or `open_authoring_decision`. Admission retains the raw observation, rule, rule authority, information preserved, and information lost or excluded.

Python chunks, graph nodes, anchors, and indexes are materialization observations. A chunk may correspond to an authored unit, be a transport split, reveal a defect, or remain unresolved. The exporter does not settle that distinction by naming its records.

## 5. Vocabulary and salvage discipline

A Python term may describe an observed artifact or behavior; it does not automatically name a clean-kernel responsibility. Ask which demonstrated responsibility or corpus fact requires representation and what narrowest clean authority can represent it. A reusable artifact must cross an explicit package, process, or protocol boundary and must not carry excess semantic authority.

Every proposed component, field, rule, or compatibility path identifies its equation or invariant, evidence, required example, counterexample, authority boundary, and concrete consumer. Prose coherence is not evidence.

## 6. Contract lifecycle

Use:

```text
candidate
provisionally accepted
corpus-validated
superseded
```

`candidate` means represented for review. `provisionally accepted` means internally coherent and mechanically tested, but not validated against the complete vault where corpus-sensitive. `corpus-validated` means it survived a versioned whole-corpus projection and applicable private-UAT contact. `superseded` means a bounded amendment was required.

Corpus-independent mechanics may become accepted without whole-corpus validation when their boundary genuinely does not depend on corpus structure. Corpus-sensitive contracts remain provisional until raw observation, admission, projection construction, real projection access, and applicable UAT. Validation is scoped to a versioned corpus snapshot and admitted evidence boundary; later corpus changes may require revalidation without retroactively invalidating the prior result.

## 7. Synthetic-fixture boundary

Synthetic fixtures isolate deterministic behavior, prove invalid structural cases, preserve regression coverage, and make edge conditions reproducible. They do not establish whole-corpus exhaustiveness, actual identifier diversity, vault topology, real occurrence or temporal coverage, or architectural acceptance. They do not validate PR #9 against the real projection.

## 8. One responsibility per stage

- boundary inference describes how the problem gestalt changes;
- deterministic folding applies declared perturbations;
- substrate observation reports authored and materialized facts;
- projection construction maps accepted facts into a frozen structure;
- projection access probes actual corpus-derived surfaces for activation;
- activation presents a bounded positive view;
- semantic-access inference connects problem regions to projected addresses;
- conformance validates structure;
- execution materializes units;
- packet assembly preserves and bounds;
- synthesis interprets.

## 9. Required order

```text
whole-corpus observation
→ contract-contact reconciliation
→ bounded contract amendment
→ real projection construction
→ complete-vault projection validation
→ real projection-access implementation
→ candidate activation revalidation
→ semantic-access inference
→ conformance
→ execution
→ packet and synthesis
→ private UAT
```

The projection-access boundary is distinct from later semantic-access execution adapters. The former performs typed activation probes over actual corpus-derived indexes or providers. The latter executes conforming plans and hydrates outputs.

The required boundary is `ProjectionActivationAccess`; its results are mechanically computed from actual corpus-derived surfaces.

## 10. Traceability and evidence preservation

For each test turn retain problem-space state, utterance and continuity, boundary contribution, perturbations, region changes, corpus snapshot, observation identity, projection identity and validation status, activation provenance, expansion telemetry, access plan, conformance, executed paths, returned identities, packet removals and mechanical reasons, synthesis input, and answer.

Any removed unit records its identity, stage, exact deterministic rule, rule authority, and remaining invariant. Semantic or coherence vetoes are not mechanical removal reasons.

## 11. Projection-first debugging

Ask whether needed structure is authored, admitted, materialized, transferred, projected, addressable in each direction, coupled to valid surfaces, and activatable or expandable. Do not compensate for missing projection with post-retrieval heuristics or assume a Python omission proves authored absence.

## 12. Fresh runs and repository discipline

A fresh baseline has a new suite and thread identity, empty state, corpus snapshot, observation identity, and projection identity. `CLEANROOM` remains independent from `semantic-traversal`. Do not import Python source, orchestration, diagnostics, or tests merely to accelerate development. Python may remain evidence, a bounded substrate/access provider, or migration/evaluation tooling. No Python runtime port is authorized.

## 13. Review gates

The gates are: kernel authority; problem-space mechanics; whole-corpus substrate contact; complete projection; real projection access; candidate activation; semantic-access plan; conformance; execution and packet; synthesis; behavioral fidelity; and explicit compatibility acceptance.

Gate C requires raw and materialized facts with discrepancies and unknowns preserved. Gate D requires validated object, region, unit, identifier, occurrence, anchor, surface, transition, and provenance closure. Gate E requires actual projection-access probes. Gate J requires private UAT preservation and improvement of demonstrated capability. PR #9 remains provisional until these applicable gates pass.

## 14. Stop conditions

Stop and return to evidence or design if a corpus-sensitive abstraction lacks evidence, a fixture is treated as whole-corpus acceptance, a candidate contract silently overrides corpus actuality, a Python boundary is copied without a consumer, unknowns receive invented defaults, a semantic role appears between execution and synthesis, or a valid result is removed for a semantic/coherence reason. Also stop if a needed path is absent from the projection and post-retrieval code is proposed instead of substrate or projection work.

## 15. Recovery boundary

CLEANROOM is not restarted. Existing contracts, fold, fixture, and PR #9 work are preserved. Further semantic-access, conformance, execution, packet, and synthesis implementation remains frozen until the corrected sequence reaches it. One eventual production kernel authority remains the target; compatibility mechanisms require concrete consumers.
